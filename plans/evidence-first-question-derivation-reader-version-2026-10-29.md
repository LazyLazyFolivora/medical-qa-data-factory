# 客观医学题目生成系统整体方案阅读版

> 适合阅读对象：产品负责人、研究人员、数据集设计者  
> 更新日期：2026-10-29  
> 对应技术计划：`evidence-first-question-derivation-refactor-plan-2026-10-28.md`

## 1. 我们要解决什么问题

我们的目标不是让模型根据一个医学实体随便写出几道看起来合理的题，而是建立一条能够持续生产客观题目的流程。

最终发布的题目必须满足：

- 题面本身完整，不依赖用户看不到的前置条件；
- 答案描述现实世界中的事实，不是某个知识图谱或数据库的收录结果；
- 答案有清楚的对错标准，可以通过独立来源复核；
- 题目没有把相关性夸大成因果、治疗效果或诊断结论；
- 无法确认客观性的候选题不能发布；
- 一个实体没有合适事实时，允许生成 0 道题。

知识图谱、CTD、PubMed 和 RAG 都可以帮助系统发现材料，但它们不能单独决定题目的含义和标准答案。

可以把核心原则概括为：

```text
数据源负责提供线索和证据
现实世界中的事实决定题目和答案
```

## 2. 什么是我们需要的客观题目

客观题目不等于“题目后面附了一篇论文”，也不等于“知识图谱中存在一条关系”。

一道题至少需要满足四个条件。

### 题面自包含

用户只看题面，就能知道主体、问题、必要条件以及预期回答形式。

不能依赖以下隐藏信息：

- 本次使用的是哪个知识图谱；
- 检索到了哪些文献；
- 内部候选集合有哪些；
- 生成过程中设置了什么过滤条件；
- 程序预先选择了哪个答案。

### 答案与数据源无关

换一个可靠来源复核时，答案不应因为数据库收录范围不同而改变。

“PrimeKG 中有哪些疾病与某药物相连”属于数据库查询，不属于我们要生产的客观医学题。

### 有明确判断标准

必须能够说明什么答案算正确、什么答案算错误。观点、建议、研究趋势和开放式评价不属于稳定客观事实。

### 可以独立验证

答案不能只由发现候选的同一条图谱边或同一段模型摘要证明。发布前需要使用适合该事实类型的独立材料进行确认，并检查是否存在其他答案或冲突证据。

## 3. 明确排除的题目

以下问题不属于最终题目空间：

- “在某知识图谱中，哪些疾病与某物质有关？”
- “数据库记录了哪些相关实体？”
- “现有研究是否支持某个关系？”
- “根据当前检索结果，答案是什么？”
- “文献中是否提到某个关系？”
- 没有范围的“与某物质有关的疾病是哪一种？”
- 无法证明完整性的“所有、唯一、最主要”；
- 仍存在显著争议，却被写成确定结论的问题；
- 证据只支持相关性，却使用“导致、治疗、预防”等表达的问题。

特别需要说明的是，“现有研究是否支持”仍然是在询问证据状态。它的答案会随检索范围、发表时间和研究评价方式变化，因此不能用来修补一个无法形成客观事实的问题。

## 4. 整体流程

系统流程可以分为七步。

```text
目标实体
   ↓
收集证据材料
   ↓
理解材料并提出候选事实
   ↓
整理和筛选候选事实
   ↓
提出候选问题和候选答案
   ↓
独立验证答案并冻结问题含义
   ↓
生成最终题面并进行发布复核
   ↓
整理元数据并保存
```

这不是一条完全依赖固定规则的流水线。非结构化论文和 RAG 文本需要 LLM 理解语义，但 LLM 第一次提出的事实、问题和答案都只能是候选。

## 5. 第一步 根据目标实体收集证据材料

用户输入一个目标实体，例如一种药物、疾病、基因、蛋白质或暴露物。

系统可以调用：

- PrimeKG 等知识图谱；
- CTD 等结构化医学数据库；
- PubMed 等文献来源；
- RAG 检索；
- 后续接入的权威分类、药理或生物医学数据库。

这一阶段收集到的是“材料”，不是已经确认的事实。

材料可能包括：

- 一条图谱关系；
- 一条 CTD 记录；
- 一篇论文或摘要；
- RAG 返回的一段原文；
- 来源名称、版本、时间和原文位置。

图谱边可能不完整，论文可能只适用于特定人群，RAG 结果也可能断章取义。因此，这些内容不能直接作为标准答案。

## 6. 第二步 理解和整理候选事实

这一阶段需要 LLM 参与，因为固定规则很难完整理解非结构化医学文本中的同义词、否定、指代、人群、剂量和关系强度。

例如，一段论文可能表达：

> 在某类人群中，较高的 X 暴露与 Y 疾病风险升高相关。

LLM 可以将它整理成候选事实：

```text
主体：X 暴露
关系：与风险升高相关
客体：Y 疾病
人群：某类人群
方向：升高
关系强度：相关性，不是因果性
来源：PMID、段落和原文位置
```

随后系统需要完成：

- 实体名称和同义词统一；
- 关系方向统一；
- 重复材料合并；
- 区分支持、反对和不确定材料；
- 区分分类、位置、功能、关联、风险、因果和治疗效果；
- 保存事实对应的原文位置。

LLM 在这里负责理解和提出解释，但不能自行宣布事实已经通过验证。

## 7. 第三步 从事实中探索可以问什么

候选事实中可能包含多个信息位，例如：

| 信息位 | 可能形成的问题 |
|---|---|
| 实体身份 | 某个缩写或名称指什么实体 |
| 实体类别 | 某个实体属于什么类别 |
| 基因位置 | 某基因位于哪条染色体 |
| 生物学关系 | 某基因编码什么蛋白质 |
| 参与过程 | 某蛋白参与什么过程 |
| 数值 | 某个明确测量值是多少 |
| 封闭比较 | 在题面列出的选项中哪个符合条件 |

LLM 可以基于这些信息位同时提出：

- 候选问题；
- 候选答案；
- 需要写进题面的条件；
- 支持该答案的原文位置；
- 关系强度和可能风险。

这里允许问题和答案一起产生。关键不是禁止 LLM 提出答案，而是不能把第一次生成的答案直接当成标准答案。

## 8. 第四步 筛选事实并独立验证答案

在最终题面定稿前，系统需要确认候选问题和候选答案之间的关系是否可靠。

这里的“独立验证”不表示不能使用 LLM。它表示验证过程不能只相信前一个 Agent 的结论，也不能只重复读取发现候选时使用的同一条记录。

验证需要检查：

- 这是不是现实世界中的事实；
- 答案是否脱离原知识图谱仍然成立；
- 是否存在其他同样正确的答案；
- 必要的人群、物种、时间、剂量或定义是否完整；
- 是否存在冲突或反例；
- 证据是否只支持较弱关系；
- 答案是否具有稳定的判断标准；
- 独立材料是否能够直接支持答案。

验证后形成一个冻结的问题和答案说明：

```text
问题实际询问的事实
答案类型
正确答案
答案数量
必须公开的条件
支持答案的材料
发现过的竞争答案和冲突证据
```

这个说明的作用是防止最终题面悄悄改变已经验证过的含义。

## 9. 第五步 生成最终题面和可审计推导链

问题设计子 Agent 在题面实现模式下，根据已经验证的问题和答案说明生成自然语言题目。

它可以调整语言风格，但不能：

- 修改事实；
- 自己更换答案；
- 删除会影响答案的条件；
- 把相关性改成因果性；
- 加入“现有研究是否支持”；
- 用“在某数据库中”掩盖答案范围问题。

系统还需要保存“可审计推导链”，例如：

```text
材料 A 的第 3 段
  → 支持候选事实 F1

独立来源 B
  → 确认事实 F1

事实 F1 + 公开条件 C
  → 得到答案 A

答案 A + 问题含义 Q
  → 生成最终题面
```

这里保存的是来源定位、事实映射和使用过的判断规则，不是模型自由生成的长篇思维过程。后者难以复现，也可能包含猜测。

## 10. 第六步 题目复核

最终题面生成后，由独立复核 Agent 使用 `objective-question-validator` skill 进行发布前审查。

复核分为两层。

### 只看公开题面

先不看内部材料，检查：

- 题面是否自包含；
- 是否存在隐藏条件；
- 是否依赖知识图谱或检索范围；
- 实体是否明确；
- 单答案或多答案是否清楚；
- 是否在问客观事实；
- 是否出现因果或治疗效果夸大。

### 复核答案和证据

再检查：

- 答案是否被独立材料直接支持；
- 是否存在其他符合题面条件的答案；
- 是否存在可靠的冲突证据；
- 题面、答案和证据的方向是否一致；
- 题面是否改变了已经验证的问题含义。

最终只有三种结果：

```text
PASS           可以发布
REJECT         已发现明确问题
INDETERMINATE  无法证明正确
```

只有 `PASS` 可以进入正式题目集。

## 11. 第七步 整理元数据并保存

元数据不能等最后一步才开始保存。系统应当从材料检索开始持续记录每一步，最后再整理成两个结果包。

### 公开题目包

面向答题者或数据使用者，包含：

- 题目；
- 标准答案；
- 简洁解释；
- 必要时提供公开引用。

### 内部审计包

面向审核和复现，包含：

- 目标实体；
- 原始材料及其版本；
- 图谱边、CTD 记录、PMID 和原文位置；
- 候选事实和被拒绝事实；
- 候选问题和候选答案；
- 答案范围及竞争答案检查；
- 结构化推导链；
- 客观题验证报告；
- 模型、prompt、skill 和数据版本；
- 工具错误、调用成本和失败原因。

即使最后生成 0 道题，也要保存为什么没有题目通过。

## 12. 系统需要哪些页面

当前项目已经使用 Vue 3 和 Vite，不需要为了这次改造重写成 React。React 或 Vue 只负责页面展示，不决定题目是否客观。

### 题目生成工作台

用户选择：

- 目标医学实体；
- 希望生成的题目数量；
- 难度；
- 面向人群和表达风格。

页面展示：

```text
正在收集材料
→ 发现 26 个候选事实
→ 11 个不适合形成客观题
→ 8 个答案范围不明确
→ 4 个独立验证失败
→ 3 道题通过
```

数量是上限，不是必须完成的指标。

### 任务详情页面

展示一次任务的完整过程：

- 调用了哪些来源；
- 找到了多少材料；
- 提取了哪些候选事实；
- 每个候选为什么通过或失败；
- 当前运行到哪个阶段；
- 是否发生数据源错误。

页面应使用业务语言，例如“答案不唯一”或“依赖隐藏数据库范围”，而不是只显示开发错误码。

### 题目审核页面

左侧展示公开题目、答案和解释，右侧展示事实来源、原文定位、结构化推导链和复核结果。

### 质量统计页面

展示：

- 候选事实数量和最终通过率；
- 各类拒绝原因；
- 人工审核推翻率；
- 客观题误放行率；
- 数据源错误率；
- 每道通过题目的平均成本。

## 13. 系统需要哪些普通模块

并不是所有环节都应该由 Agent 完成。确定性的事情需要由普通程序控制。

| 模块 | 负责解决什么问题 | 推荐形式 |
|---|---|---|
| 用户页面 | 发起任务并查看结果 | 现有 Vue 3 加 Vite |
| 后台接口 | 接收请求并返回任务状态 | 现有 Python 加 Starlette |
| 流程协调器 | 托管主 Agent，控制步骤顺序、失败恢复和状态流转 | Python 工作流或状态机 |
| 数据源连接器 | 统一访问图谱、CTD、PubMed 和 RAG | 固定接口 |
| 材料仓库 | 保存原文、来源位置和数据版本 | 结构化存储 |
| 实体与关系整理 | 统一名称、方向和关系强度 | 规则加模型辅助 |
| 答案范围检查 | 检查唯一、多答案和完整性 | 固定程序为主 |
| 发布门禁 | 只允许 PASS 题目发布 | 确定性程序 |
| 审计仓库 | 保存推导链、验证报告和版本 | 结构化存储 |

Agent 可以提出解释和候选，发布门禁不能由 Agent 自由决定。

## 14. 系统需要哪些 Agent

系统采用“一个主 Agent 加五类子 Agent”的层级结构。主 Agent 对一次完整任务负责，子 Agent 只完成被分配的专业工作。

```text
确定性任务协调器
        ↓
题目生产主 Agent
   ├─ 材料检索子 Agent
   ├─ 事实理解子 Agent
   ├─ 问题设计子 Agent
   ├─ 答案验证子 Agent
   └─ 发布复核子 Agent
        ↓
确定性发布门禁
```

### 题目生产主 Agent

主 Agent 接收目标实体、目标题数、难度、风格和运行预算，对整次生成任务进行规划和调度。

它负责：

- 制定材料检索计划；
- 按需调用不同子 Agent；
- 汇总子 Agent 返回的结构化结果；
- 根据证据缺口决定是否继续检索；
- 管理候选事实和候选题池；
- 控制轮次、成本、超时和停止条件；
- 将合格候选送入答案验证和发布复核；
- 向页面报告进度、失败原因和 0 题结果。

它不能：

- 自己宣布候选答案客观正确；
- 修改子 Agent 已经固化的材料、事实和验证结果；
- 把 `REJECT` 或 `INDETERMINATE` 改成 `PASS`；
- 绕过确定性发布门禁；
- 为了达到目标题数降低质量标准。

### 材料检索子 Agent

根据主 Agent 下发的检索任务，调用知识图谱、CTD、PubMed 和 RAG，收集原始材料及其位置。

同一种子 Agent 可以创建多个实例，分别负责不同来源。每个实例只返回材料、来源位置、检索记录和错误，不负责解释最终事实。

它无权决定标准答案，也无权发布题目。

### 事实理解子 Agent

负责理解结构化和非结构化材料，提取候选事实、必要条件、关系强度以及支持、反对或不确定信息，并把每个解释绑定到原文位置。

它只解决“材料在说什么”，不能为了方便出题而修改事实，也不能直接生成正式题目。

### 问题设计子 Agent

读取已经固化的候选事实，识别可以提问的信息位，提出候选问题、候选答案和必须公开的条件。

它只解决“这里可能问什么”。候选问题和答案的状态只能是 `PROPOSED`，不能直接成为正式题目和 gold answer。

答案通过验证后，它还可以在受约束模式下把冻结的问题说明写成自然语言题面；此时只能调整表达，不能改变答案、条件和关系强度。

### 答案验证子 Agent

负责独立查询其他来源，检查答案、竞争答案、冲突证据和问题范围，形成经过验证的问题和答案说明。

它第一轮处于盲态，不能看到问题设计子 Agent 提出的候选答案。完成独立求解后，才比较两个答案并专门搜索反例。它不能只复述前面子 Agent 的结论。

### 发布复核子 Agent

使用 `objective-question-validator` 对最终公开题面和答案做独立审查。

它与问题设计子 Agent 使用不同上下文，并且必须拆成两次互相隔离的调用：

1. 公开题面审查只接收用户会看到的题目，完全看不到答案、内部问题说明和证据；
2. 第一阶段结果固化后，答案证据审查才接收题面、答案和独立验证材料。

两个结果由普通程序合并。任何一次失败、超时或无法判断，最终都不能通过。

### 主子 Agent 如何交接

主 Agent 和子 Agent 之间只交换结构化任务和结构化结果。子 Agent 不能直接修改其他子 Agent 的产物；需要补充材料时，只能向主 Agent 返回新的 evidence need，由主 Agent 决定是否再次调度。

底层可以使用同一个模型，但必须隔离系统提示、可见上下文、工具权限和运行记录。最终发布仍由确定性门禁决定，主 Agent 和任何子 Agent 都无权绕过门禁。

## 15. 首期应该支持什么

首期优先支持最稳定、最容易形成明确判断标准的事实：

- 实体身份；
- 规范分类；
- 基因或蛋白质定位；
- 明确的组成、编码和从属关系；
- 稳定的生物学功能；
- 题面公开给出完整范围的选择题；
- 条件和单位明确的客观数值。

首期暂不自动发布：

- 开放式疾病关联题；
- 风险和因果题；
- 治疗、诊断和预后题；
- 没有闭合范围的“所有、唯一、最主要”；
- 存在明显科学争议的问题；
- 只能改写成“现有研究是否支持”的问题。

后续可以逐步扩展复杂关系，但不能为了增加题量降低客观性门槛。

## 16. 如何看待知识图谱捷径

能够从一条知识图谱边直接得到答案，不必然说明事实是错的，但也不能证明题目是客观正确的。

这类候选需要区分两个问题：

1. 该事实能否脱离知识图谱，通过独立来源确认；
2. 该题是否适合训练证据检索或多步推理能力。

如果事实能够独立确认，它可以进入一般事实问答数据集；如果回答不需要目标推理过程，则不应进入推理训练集。

如果答案只能在该知识图谱的收录范围内成立，则必须拒绝。

## 17. 分阶段推进方式

### 第一阶段 固定规则和验收样例

明确客观题定义、拒绝原因、允许的首期题型以及 0 题策略。建立正例、反例和边界样例。

### 第二阶段 建立材料和候选事实链路

接入图谱、CTD、PubMed 和 RAG，保存原始材料、来源位置和版本。由 LLM 提取候选事实，但不直接发布。

### 第三阶段 建立问题探索和答案验证

允许 LLM 提出候选问题和答案，随后通过独立来源检查唯一性、完整性、冲突和关系强度。

### 第四阶段 接入题面生成和客观题复核

根据经过验证的问题和答案说明生成题面，并使用 `objective-question-validator` 进行发布前复核。

### 第五阶段 完成页面和审计闭环

在生成工作台、任务详情和审核页面中展示进度、拒绝原因、来源定位和结构化推导链。

### 第六阶段 扩大事实类型并优化成本

根据真实审核结果逐步扩展题型，优化检索、模型调用、缓存和批量处理，但不改变发布硬门槛。

## 18. 改造完成后的判断标准

改造完成后，系统应该做到：

1. 用户只需要选择目标实体和产品参数；
2. 系统能够从多个来源收集并理解材料；
3. LLM 可以探索问题，但不能自证答案；
4. 每道题都能定位到原始材料和独立验证材料；
5. 每道题都有可复现的结构化推导链；
6. 每道题都经过公开题面检查和独立答案复核；
7. 非 PASS 题目无法进入正式数据集；
8. 没有合格事实时能够正常返回 0 题；
9. 用户能够看懂题目为什么通过或为什么失败；
10. 系统能够保存完整过程用于复现和质量分析。

最终技术路线可以概括为：

> 页面负责发起任务和展示结果；题目生产主 Agent 负责规划和调度，五类子 Agent 分别完成检索、事实理解、问题设计、答案验证和发布复核；普通程序负责状态、版本和发布门禁；数据源只提供材料，只有经过独立验证的现实事实才能成为最终题目。
