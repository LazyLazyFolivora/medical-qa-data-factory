# 面向 query-planner 的批量并发出题设计

日期为 2026-11-05。本文是待实施方案，描述如何把现有单实体出题流程扩展为可暂停、可恢复的批量数据集生产流程。线程数和试运行规模是建议初值，需根据真实运行调整。

## 目标与边界

系统从配置好的实体来源自动选取尚未处理的实体，检索资料、生成并验证问题，持续汇总为 query-planner 可消费的数据集。用户配置实体范围和运行策略，启动后由系统不断领取下一个实体。批量运行期间能够查看逐实体进度和具体错误，暂停或进程重启后能够从已保存的断点继续。

题目必须客观正确、题干自足，且符合 query-planner 的真实工具环境和查询风格。数据集需要覆盖选源、实体消歧、条件约束、多步关联和证据充分性判断。简单字段查询可以保留，难度以实际解题需求评估。

现有单实体链路负责题目质量。新增调度层负责实体队列、并发、恢复、批次预算和数据集汇总。query-planner 负责实际求解、记录 rollout 和生成策略训练标签。生成器的内部检索轨迹只作审计资料，不能直接当作 planner 的标准解题路径。

跨项目字段和验收以 [总体架构](../query-planner-training-data-architecture.md) 和 [验收规范](../query-planner-training-data-acceptance-criteria.md) 为依据。现有客观问题发布格式到目标训练契约的映射，需要在联调中明确并标记版本。

## 当前基础

当前 Web 使用全局生成锁，一个进程同时执行一个生成任务。单任务循环按动作依次执行，保存断点后进入下一步。运行记录的线程锁只保护同一进程内的访问。

因此，直接删除全局锁或启动多个 Web 进程并不能建立可靠的并发任务系统。需要先建立持久化领取机制，并检查模型客户端、工具连接和共享输出的并发访问。

## 执行流程

```text
实体来源 → 查询处理记录 → 自动领取未处理实体 → worker 线程池
                                   ↓
                       每个 worker 执行一个实体任务
                                   ↓
                  检索 → 出题 → 独立验证 → 发布或补证
                                   ↓
                       保存结果和实体处理状态，自动领取下一个实体
                                   ↓
                   跨实体去重 → 质量评审 → 数据集导出
```

第一版采用单个调度进程和固定大小线程池，建议从 2 个 worker 开始。同一实体任务内部保持当前顺序执行。每个实体具有独立 run_id、运行目录和上下文。

Web 启动持续生产任务后返回任务标识，页面通过查询接口获取进度。运行会话及导出批次用于追踪生产过程，实体处理记录跨运行会话保留。调度执行与 HTTP 请求生命周期分离，关闭页面不会终止批次。单实体生成入口也通过同一领取机制执行，以免绕过资源限额。

## 实体队列与持久化状态

首次启动时配置实体来源、类型筛选、遍历顺序或抽样种子。调度器分页遍历来源，结合持久化处理记录自动选取未处理实体。游标用于加速遍历，实体账本用于判断是否处理过，领取和写入领取状态在同一事务内完成。按 provider、实体类型和稳定 ID 去重，名称作为展示字段。来自不同来源的等价实体需要实体映射，不能仅靠名称合并。

生产任务保存来源与筛选条件、来源快照、遍历位置、目标题数、难度目标、并发配置、预算、模型与 skill 版本，以及启动和暂停记录。每个实体条目保存对应 run_id、状态、重试次数、最后错误、领取者和租约信息。

建议使用独立的调度 SQLite 数据库管理队列。每个线程使用自己的连接，用短事务原子领取任务，开启 WAL 并配置合理的忙等待。模型和网络请求在事务外执行。PrimeKG 保持作为独立数据源，队列不写入知识图谱数据库。

实体任务状态如下。

| 状态 | 含义 | 下一步 |
|---|---|---|
| pending | 尚未领取 | 可用 worker 领取 |
| running | 正在运行 | 保存进度并续租 |
| retry_wait | 临时故障 | 到期后重新领取同一 run_id |
| paused | 已保存断点并暂停 | 用户恢复后入队 |
| completed | 实体探索按规则结束 | 汇总产出及结束原因 |
| failed | 无法自动恢复 | 显示具体错误，允许修复后重试 |

completed 可以是零题，必须附带结束原因。预算耗尽和探索方向耗尽分别记录。检索服务不可用不能标记成方向已经查完。

领取操作写入递增的执行代号和租约到期时间，心跳独立于长时间模型请求。恢复前先确认旧执行者已经退出或失去提交资格。状态提交与发布必须核对当前执行代号，防止旧 worker 恢复响应后覆盖新结果。不能仅凭租约超时就让两个执行者同时写单任务文件。

## 已处理实体的判定与循环结束

实体处理账本独立于单次运行和导出批次。每条记录关联稳定实体身份、处理版本、run_id、当前状态、产出数量和结束原因。已完成且零产出的实体同样记为已处理，避免无休止地重新出题。

临时故障进入等待重试，永久失败单独记录；两者都不能伪装成已经充分探索。恢复已有任务时沿用原 run_id。单个实体达到预算上限后记录明确原因，默认跳过；用户可通过显式重跑策略重新安排。

默认情况下，重启服务、创建新的运行会话或导出数据集都不会清空处理账本。模型、skill 或数据源版本改变时保留原记录，通过明确的重新处理策略创建新处理版本，避免每次升级自动重跑全部实体。原处理记录和产出始终可追溯。

多个 worker 必须共享同一账本，实体身份与处理版本具有唯一约束。读取“尚未处理”并不能占有任务，只有原子领取成功的 worker 可以执行。分页游标推进不能越过尚未持久化的任务，以免崩溃后漏处理。

持续生产直到用户暂停、配置的预算或产出目标达到，或当前实体范围已遍历完毕。实体耗尽时展示已处理数量和剩余重试任务，不重新从头重复出题。来源后续新增实体时可再次扫描并跳过账本中已有条目。

## 并发与资源控制

worker 数、模型请求并发和各检索源请求速率独立配置。例如两个 worker 可以共享一个模型请求名额，等待模型时仍可进行允许的检索。

SQLite 连接按线程隔离。模型客户端和 HTTP 会话在确认线程安全之前按 worker 创建。共享缓存使用原子写入；队列、单任务状态和数据集汇总分别明确写入归属。第一版由单个汇总者提交数据集条目。

每个实体沿用当前候选补证上限和外层探索预算。外层预算按题数上限乘以 3，再乘以难度系数计算，简单为 1、中等为 2、困难为 4，多难度取最高系数。

批次另设模型调用、成本或运行时间上限。到达上限时停止领取新实体，已有任务在可恢复边界保存状态。调用前预留额度，避免多个 worker 同时看到剩余额度而超支。

## 故障、重试与暂停

每次工具调用记录数据源、查询、时间、耗时、终止状态、错误类别和具体异常。HTTP 状态码、超时类型和重试建议在工具能提供时一并保存。日志需遮蔽密钥和鉴权参数。

| 情况 | 处理 |
|---|---|
| 成功但没有结果 | 记录已尝试方向，选择其他方向 |
| 网络超时、限流或临时服务错误 | 有上限地退避重试，必要时换源或进入 retry_wait |
| 查询参数不合法 | 带具体错误修正请求，不盲目重试同一参数 |
| 配置、凭据或本地数据源故障 | 暂停受影响任务，提供可操作的诊断 |
| 候选缺少证据 | 进入单实体的定向补证循环 |
| 多实体同时发生同源故障 | 暂时停止向该来源发请求，避免整批耗尽预算 |

成功查询才用于判断方向是否充分探索。故障尝试仍计入实际成本和独立的失败重试限额，不能形成无限重试。每次重试沿用任务身份和已保存结果，发布时按稳定题目 ID 幂等写入。外部调用在崩溃后可能重复产生费用，应记录不确定的调用状态。

暂停批次时先停止领取新实体，再向活动任务发出暂停请求。界面区分“正在暂停”和“已暂停”。网络请求有超时，任务在安全边界保存断点。恢复时重新读取持久化队列和单实体断点。

## 数据集分布、去重与导出

每实体产出目标与批次分布目标分开设置。中等目标任务可以保留合格简单题，但简单题不计入中等配额。批次汇总同时展示总发布量和计入目标的数量，避免统计混淆。

第一版持续遍历配置范围内的未处理实体，并报告难度和能力覆盖缺口。根据缺口自动选择下一批实体属于后续能力，不能在实体资料不足时硬凑题。实体池用尽或预算用尽时，报告实际产出和未达到的目标。

达到批次目标时停止领取新任务，活动任务在安全边界结束或暂停。并发产生的超额合格题保留在运行结果中，正式导出由汇总者按固定策略选取，避免竞态导致数量超限。

导出分为 planner 可见问题和隐藏评估资料。隐藏资料保存答案、直接支持证据、来源和版本、评审结果及题目来源批次。与 planner 对齐工具可访问性，确认生成器依赖的证据是否在评估环境中可获得。

先按题干及目标实体、关系做确定性去重，再对疑似语义重复进行复核。切分训练集和测试集时检查同实体、同研究或高度相近证据造成的泄漏，并在 manifest 中说明采用的分组策略。

## 页面与接口

批次页展示待处理、运行中、等待重试、暂停、完成和失败的实体数，以及总发布量、目标计数、资源消耗和覆盖分布。实体行链接到已有运行详情页。

提供创建、查询、暂停、恢复和导出批次的接口。具体路径在实现时遵循现有 API 风格。故障信息可以按数据源聚合，并展开查看单次失败查询。界面不能用统一的“完成，零题”替代服务故障。

## 实施顺序与验收

1. 建立持久化实体处理账本和自动领取逻辑，用单 worker 持续遍历未处理实体，复用现有出题流程。
2. 完成领取、暂停和进程重启恢复，验证同一任务不会重复提交。
3. 开启两个 worker，隔离连接和上下文，接入全局模型及数据源限流。
4. 汇总已发布题，完成跨实体去重、导出和 query-planner 联调。
5. 用小规模真实批次评估质量和吞吐后再调整并发，随后考虑按覆盖缺口补充实体。

建议首次试运行自动处理 10 个实体后暂停检查。恢复生产时继续领取其余未处理实体，已完成实体必须自动跳过。验收需证明两个实体实际并行、其中一个失败不阻塞其他实体、暂停和重启可恢复、重复领取不会重复发布、网络故障不会被当作探索完成。使用可控故障测试验证超时、限流和写入中断。

人工审阅抽样题目的正确性、自足性和实际检索价值，并让 query-planner 在约定工具环境中解题。记录答案与证据通过情况、检索步数和成本。生产放量依据联调结果及跨项目验收规范确定，不以 worker 跑完或题数达标替代质量验收。

线程池提供并发执行，不提供安全沙箱。当前受控工具调用可先使用最小文件权限和按任务隔离的目录。若后续允许执行模型生成代码，再引入独立进程或容器，并处理模型服务地址、数据库只读挂载、持久化卷和资源限制。
