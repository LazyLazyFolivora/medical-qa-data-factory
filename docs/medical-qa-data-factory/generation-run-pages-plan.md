# 生成任务展示页与详情页信息架构

## 1. 目标

把“每一次生成”（generation run）作为独立、可浏览、可分享、可追溯的产品对象。

页面需要回答四个问题：

1. 我生成过哪些任务？
2. 某次任务现在运行到哪里，是完成、失败、停滞还是正常产出 0 题？
3. 这次任务产生了哪些候选假设、证据和最终题目？
4. 每道最终题来自哪条事实、哪份原文证据和哪次发布复核？

本文描述页面信息架构和交互边界，不涉及具体代码实现。

## 2. 当前问题

当前生成工作台已经具备实体选择、生成配置、实时状态、发布题目、候选折叠和技术轨迹等能力，但页面仍以“一次当前会话”为中心，主要存在以下问题：

1. 创建、运行监控、结果阅读和技术诊断集中在同一个长页面，信息层次过多。
2. 历史任务只通过下拉框切换，缺少可浏览的生成记录列表。
3. 运行详情通过弹窗展示，不能形成稳定、可分享的详情页。
4. URL 仍以查询参数为主，任务、页面页签和具体题目缺少清晰、稳定的路径。
5. 候选假设数容易被看成已生成题数，用户不能快速判断“有多少候选”和“有多少正式发布题”。
6. 进度使用“发布数 / 目标题数”的比例表达；目标题数只是上限，因此正常产出少于目标时会被误认为尚未完成。
7. 失败、停滞、正常 0 题、需要恢复等终态需要更明确的视觉和文案区分。

## 3. 设计原则

### 3.1 一次生成就是一个独立对象

每次生成必须拥有稳定 `run_id`，所有页面、页签、分享链接和导出信息都以该 ID 为根。

生成结束后记录仍然保留。刷新页面、重启前端或重新进入系统后，必须能够找回该任务。

### 3.2 创建、历史、详情分离

- 首页只负责创建新任务和提供最近任务入口。
- 历史页负责浏览、搜索和筛选所有任务。
- 详情页负责观察单次任务、审查结果和追溯证据。

### 3.3 结果优先，过程次要

普通用户先看到任务结论、最终题目和停止原因。

主 Agent 决策、子 Agent 调用、原始产物和错误栈放在执行轨迹或诊断页签中，不占据首屏主体。

### 3.4 数据身份不能混用

页面必须始终区分以下对象：

- 候选问题假设：`question_hypothesis`
- 候选事实：`candidate_claim`
- 答案核验：`answer_resolution`
- 冻结题目契约：`frozen_question_contract`
- 题面草稿或正式题面：question draft / public question
- 最终发布题：发布包中的 `public/question`

候选假设不能显示成“已生成 N 题”。

### 3.5 状态必须反映真实语义

至少区分：

- 已创建，等待运行
- 运行中
- 正在重试
- 长时间无进展
- 正常完成
- 正常完成但产出 0 题
- 因模型或 Provider 错误失败
- 需要人工恢复
- 版本不兼容
- 已取消

“0 题”本身不是错误。只有技术失败、停滞或恢复失败才应显示为错误状态。

### 3.6 单次错误不能直接终止任务

模型或外部服务返回一次错误时，系统应先判断错误类型并在边界内重试。

只有以下情况才进入需要恢复或失败状态：

- 重试次数和修复策略已经耗尽
- 请求本身无法通过修复继续
- 预算、权限或数据版本已不允许继续

任务进入“需要恢复”后必须保留最后有效检查点，并允许使用同一个 `run_id` 从下一步继续。

## 4. 信息架构

建议采用三层结构：

```text
生成工作台（创建）
    └─ 创建后进入生成详情

生成记录（全部历史）
    └─ 生成详情
        ├─ 概览
        ├─ 执行轨迹
        ├─ 候选假设
        ├─ 证据材料
        ├─ 已发布题目
        └─ 诊断与导出

题目详情
    ├─ 题面、答案和解释
    ├─ 发布复核
    ├─ 来源假设
    └─ 原文证据
```

一级导航建议为：

- 生成工作台
- 生成记录
- 题库（后续阶段，可复用本文的题目详情设计）

## 5. 页面与路由

| 页面 | 建议路径 | 作用 |
| --- | --- | --- |
| 生成工作台 | `/generate` | 创建新生成任务，展示最近任务 |
| 生成记录 | `/runs` | 浏览、搜索和筛选历史生成 |
| 生成详情概览 | `/runs/:runId` | 单次任务的总览和结果入口 |
| 执行轨迹 | `/runs/:runId/execution` | 主 Agent、子 Agent、动作和步骤 |
| 候选假设 | `/runs/:runId/candidates` | 候选事实、核验状态和拒绝原因 |
| 证据材料 | `/runs/:runId/evidence` | 检索来源、材料、原文锚点和引用 |
| 已发布题目 | `/runs/:runId/questions` | 本次运行发布的最终题目 |
| 诊断与导出 | `/runs/:runId/diagnostics` | 错误、预算、运行产物和导出 |
| 题目详情 | `/questions/:questionId` | 题面、证据链和发布上下文 |

路径名称是产品层约定。实现时可以按现有路由能力调整，但不应退回到只能使用 `/?run=...` 的临时入口。

## 6. 生成工作台

生成工作台只负责创建下一次生成。

### 6.1 主要内容

1. 实体选择与当前实体摘要。
2. 目标题数上限。
3. 难度、提问风格和材料 Provider。
4. 模型或生成引擎状态。
5. 开始生成主操作。
6. 最近任务列表或最近三次生成摘要。

### 6.2 创建后的行为

点击“开始生成”后：

1. 立即创建新 `run_id`。
2. 跳转到 `/runs/:runId`。
3. 在详情页持续展示当前阶段与最近进展。
4. 不允许因页面刷新而丢失当前任务。
5. 当前已有任务运行时，明确展示阻塞原因，不创建第二个静默排队任务。

### 6.3 最近任务

最近任务至少显示：

- 实体
- 创建时间
- 当前状态
- 已发布题数
- “查看详情”入口

最近任务不是完整历史，完整列表进入“生成记录”。

## 7. 生成记录页

生成记录页用于浏览所有已保存的运行。

### 7.1 列表字段

| 字段 | 说明 |
| --- | --- |
| 实体 | 名称、symbol 或实体类型 |
| 生成时间 | 创建时间和最后更新时间 |
| 状态 | 运行中、完成、0 题完成、失败、停滞、需要恢复等 |
| 当前阶段 | 检索、事实理解、答案核验、题面冻结、发布复核等 |
| 主 Agent 步数 | 已完成决策步数和动作上限 |
| 候选数量 | 候选假设数，不称为题数 |
| 已发布题数 | 最终通过发布复核的题目数 |
| 停止原因 | 证据耗尽、目标达成、模型错误等摘要 |
| 导出 | 可下载时展示入口 |

### 7.2 筛选与排序

至少支持：

- 按实体搜索
- 按状态筛选
- 按创建时间范围筛选
- 按最近进展排序
- 按是否发布题目筛选

### 7.3 行级操作

- 打开生成详情
- 复制任务链接
- 复制运行 ID
- 重新使用本次配置创建新任务
- 下载发布包或审计包

重新运行必须创建新的 `run_id`，不能在原运行记录上覆盖。

## 8. 生成详情页

详情页顶部使用固定运行摘要，切换页签时始终可见。

### 8.1 固定摘要

必须显示：

- 实体名称、类型和 canonical ID
- 完整 `run_id`
- 当前状态
- 当前阶段或当前动作
- 主 Agent 已完成步数
- 目标题数上限
- 候选假设数
- 已发布题数
- 最近进展时间
- 运行耗时
- 复制链接、导出或重新运行入口

数量展示示例：

```text
目标上限 10 | 候选假设 13 | 已发布题目 0
```

不能显示成含糊的“生成 13 题”。

### 8.2 概览页签

概览页回答“这次运行发生了什么”。

主要区块：

1. 生成目标与配置。
2. 生命周期阶段条。
3. 候选、验证、冻结和发布数量。
4. 最终结论。
5. 停止原因或错误摘要。
6. 已发布题目预览。
7. 关键失败点或待处理动作。

建议阶段条：

```text
目标配置
  → 证据检索
  → 事实理解
  → 候选假设
  → 答案核验
  → 题面冻结
  → 发布复核
  → 结果导出
```

每个阶段需要同时显示状态和数量，例如“检索 17 次”“候选 13 个”“已发布 2 道”。

### 8.3 执行轨迹页签

执行轨迹按实际决策顺序展示：

- 主 Agent 第几步
- 决策动作
- 目标子 Agent
- 输入产物
- 输出产物
- 花费或耗时
- 成功、失败或重试状态

交互要求：

- 当前步骤突出显示，但不遮蔽更早记录。
- 支持只看失败步骤。
- 支持展开某一决策的完整参数和输出摘要。
- 能看到失败发生在第几步、哪个子 Agent、什么错误。
- 不把技术弹窗作为唯一详情入口。

### 8.4 候选假设页签

按状态分组：

- 待处理
- 已提案
- 已核验
- 已拒绝
- 无法确定
- 已发布

候选卡片显示：

- 问题意图
- 公开条件
- 建议答案
- claim 强度
- 证据数量
- 当前核验状态
- 拒因或不确定原因

点击候选后打开详情侧栏或详情区域，展示：

```text
问题假设
  → 候选事实 claim
  → 支持证据锚点
  → 答案核验
  → 冻结题目契约
  → 发布结果
```

候选详情需要提供稳定链接。若首版不拆独立页面，也应使用类似 `?candidate=<id>` 的可分享状态。

### 8.5 证据材料页签

证据页按来源组织：

- Provider
- 检索用途
- 查询条件和轮次
- 返回状态
- 材料数和候选事实数

材料详情展示：

- 来源记录 ID
- 标题和材料类型
- 原文摘录
- 字段或章节位置
- 被哪些 claim 使用
- 支持或反驳关系
- 原文或外部来源链接

证据筛选建议：

- 按候选假设筛选
- 按 Provider 筛选
- 只看支持证据
- 只看冲突证据
- 只看被最终题目使用的证据

### 8.6 已发布题目页签

这里只展示通过发布复核的最终题目。

每题至少显示：

- 题面
- 参考答案
- 解释
- 难度
- 提问风格
- 发布复核状态
- 支持证据数量

题目与候选假设要在视觉上明确分开。候选页中的内容即使看起来像题，也不能出现在“已发布题目”中。

### 8.7 诊断与导出页签

诊断页用于开发、审阅和排障。

主要内容：

- HTTP 和模型错误
- 脱敏后的 Provider 错误响应
- Provider request ID
- 每次重试的次数、原因、耗时和结果
- 最后成功步骤和下一步恢复位置
- Schema / validation error
- 停滞或恢复信息
- 预算使用
- 模型调用次数
- runtime commit 状态
- 审计文件和发布包下载
- 原始运行摘要
- 复制相关 ID

该页允许技术信息密度较高，但不能成为普通用户理解任务状态的唯一页面。

## 9. 题目详情页

每道发布题应有独立详情页。

推荐路径：

```text
/questions/:questionId
```

页面结构：

1. 面包屑：生成记录 → 本次运行 → 题目。
2. 题面、答案和解释。
3. 难度、风格、题目类型和发布状态。
4. 题目契约和公开条件。
5. 来源候选假设。
6. 支持证据和冲突证据。
7. 答案核验与发布复核。
8. 本次运行的固定上下文和返回链接。

同一道题可能后续被修订，因此需要展示版本信息。至少区分：

- 首次发布版本
- 当前版本
- 被哪个运行发布
- 是否有后续审核或修订

## 10. 状态和数量语义

### 10.1 状态标签

| 内部状态 | 用户文案 | 视觉语义 |
| --- | --- | --- |
| `pending` / `created` | 等待运行 | 中性 |
| `running` | 运行中 | 进行中 |
| `retrying` | 正在重试 | 警告但仍在运行 |
| `stalled` | 长时间无进展 | 警告 |
| `completed` | 已完成 | 成功 |
| `completed_with_zero_questions` | 已完成，0 题 | 成功但结果为空 |
| `provider_failed` | 外部服务失败 | 错误 |
| `recovery_required` | 等待从断点继续 | 错误或待处理 |
| `version_incompatible` | 版本不兼容 | 错误 |
| `cancelled` | 已取消 | 中性 |

### 10.2 进度

运行进度应基于生命周期阶段或实际步骤，不使用“发布题数 / 目标上限”。

目标题数只是上限。比如目标上限为 10、最终正常发布 2 题，页面应显示：

```text
目标上限 10
实际发布 2
状态：已完成（证据候选已耗尽）
```

而不是把任务显示为“完成 20%”。

### 10.3 停止原因分类

停止原因至少区分：

- 已达到可用候选上限
- 证据候选耗尽
- 发布复核对所有候选完成审查
- 预算耗尽
- 模型服务失败
- 外部 Provider 失败
- 技术校验失败
- 自动重试耗尽
- 用户取消

“证据不足导致 0 题”和“程序失败导致 0 题”必须使用不同文案和颜色。

## 11. 重试与断点继续

### 11.1 模型调用重试

每次结构化模型调用都必须经过统一的失败分类和重试策略。

自动重试的默认范围包括：

- 网络错误
- 超时
- HTTP 429
- HTTP 5xx
- Provider 明确标记为暂时不可用的响应

HTTP 400 不能直接视为永久失败。系统必须保存脱敏后的响应体，并根据错误内容判断是否可修复，例如：

- 上下文过长：裁剪或摘要低优先级上下文后重试
- 不支持的请求参数：移除兼容层不支持的可选参数后重试
- 结构化输出不兼容：切换到该 Provider 支持的输出模式
- Prompt 或消息顺序不合法：修复请求结构后重试
- Provider 网关误报：执行有限次数的退避重试

若响应表明请求包含无法修复的问题，例如模型不存在、账号无权限或输入违反服务策略，则不应无限重试，但必须准确记录原因。

重试必须满足：

1. 总尝试次数有上限，且可配置。
2. 使用指数退避，避免短时间内连续打满 Provider。
3. 每次尝试都记录状态码、错误类别、request ID、耗时和是否使用了修复策略。
4. 不把 API Key、完整医疗材料或敏感个人信息写入错误日志。
5. 自动降级到另一个模型或 Provider 时必须有显式记录，不能静默切换。

### 11.2 检查点语义

下列事件发生后都应形成可恢复检查点：

- 主 Agent 决策提交
- 子 Agent 结果提交
- 材料或证据锚点提交
- 答案核验提交
- 题目契约提交
- 发布复核提交
- 运行状态切换

检查点至少要记录：

- 当前 `run_id`
- runtime commit 序号
- 主 Agent 已完成步骤
- 最后成功的决策和动作
- 已提交的子任务、产物和幂等键
- 下一次应执行的动作或决策
- 当前重试次数
- 最后错误摘要

### 11.3 断点继续

用户点击“从断点继续”后：

1. 继续使用原 `run_id`，不创建新的生成记录。
2. 加载最后一个有效检查点。
3. 确认已提交的子任务和产物不会再次写入。
4. 从失败发生前的下一步继续主 Agent 决策。
5. 将恢复动作和新的重试记录追加到运行历史。

若失败发生在模型返回之前，模型决策调用可以直接重放，因为它没有外部副作用。

若失败可能发生在有副作用的操作中，恢复时必须依赖明确的幂等键：

- 已提交的检索请求不重复收费或重复写入
- 已提交的证据锚点不重复生成
- 已完成的子 Agent 不重复执行
- 已发布的题目不重复发布

### 11.4 用户可见流程

自动重试期间，页面持续显示任务为“正在重试”，例如：

```text
第 17 步已完成
第 18 步主 Agent 决策失败，正在重试 2/3
预计处理：缩短上下文后重试
```

重试成功后直接恢复运行，不要求用户重新创建任务。

重试耗尽后，页面显示：

```text
最后完成：第 17 步
失败位置：第 18 步主 Agent 决策
原因：HTTP 400，上下文长度超过 Provider 限制
操作：从第 18 步继续
```

恢复状态不能显示成普通的“生成失败”，也不能把候选数量或已有产物丢弃。

### 11.5 当前设计针对的典型场景

如果第 17 步的材料检索已成功提交，而第 18 步主 Agent 决策返回一次 HTTP 400：

1. 不得直接把整个 run 终止为不可继续状态。
2. 必须先按错误类型执行修复和有限重试。
3. 若重试仍失败，应保存“第 17 步已完成、下一步为第 18 步”的检查点。
4. 用户继续时从第 18 步重新请求主 Agent 决策，不能重跑第 17 步。

## 12. 页面状态

所有任务页面都需要完整处理：

- 首次加载
- 内容为空
- 正常运行
- 实时更新
- 正在自动重试
- 长时间无进展
- 失败
- 可恢复暂停
- 正在从断点继续
- 0 题完成
- 非 0 题完成
- 不存在或无权访问

页面刷新不应改变当前选中的运行。详情页刷新后仍应停留在同一任务和同一页签。

## 16. 验收标准

1. 任意一次生成都能从历史列表进入固定详情页。
2. 刷新详情页或重启前端后仍可找到同一运行。
3. 运行中、完成、0 题完成、失败、停滞和需要恢复在列表中可区分。
4. 候选假设数不会显示为已生成题数。
5. 目标题数展示为上限，不影响终态判定。
6. 生成详情能查到主 Agent 当前处于第几步和最新动作。
7. 失败任务能定位到具体决策步骤、子 Agent 和错误。
8. 发布题能从题目详情追溯到来源假设和原文证据。
9. 技术轨迹、候选详情和证据详情不是因为弹窗关闭而丢失的临时数据。
10. 页面在桌面和手机宽度下都能完成“查看历史 → 打开详情 → 查看题目 → 查看证据”的主路径。
11. 单次 HTTP 400 不会直接把任务终止，必须先进入分类和有限重试流程。
12. 错误记录包含步骤、动作、角色、状态码、request ID、重试次数和脱敏响应摘要。
13. 自动重试成功后任务继续运行，已有步骤和产物不重复。
14. 重试耗尽后页面能明确显示最后成功步骤、失败位置和下一步恢复位置。
15. “从断点继续”使用原 `run_id`，并从正确的下一步恢复。
16. 恢复过程中不会重复提交已完成的检索、子任务、证据、题目或发布结果。
17. 重试和恢复历史在详情页可查询。

## 17. 不在本文范围内

- 人工审核工作流的具体审批权限
- 数据集拆分和训练数据导出规则
- 候选问题的医学正确性判定标准
- 不同 Provider 的具体请求格式兼容规则
- 多 Provider 自动质量对比和路由策略
- 多个生成任务并行执行的调度策略

这些能力可以建立在本文定义的生成记录、候选、题目和证据详情之上，但需要单独设计。

2026-10-31 已按本文完成第一版页面与恢复能力：

- 新增稳定的 `/generate`、`/runs`、`/runs/:runId` 和
  `/questions/:questionId` 前端入口。
- 生成记录页支持按实体或 Run ID 搜索，并区分运行状态、候选假设数和发布题数。
- 运行详情页提供概览、执行轨迹、候选假设、证据材料、已发布题目和诊断页签。
- 运行详情使用固定 `run_id` 链接，旧的 `/?run=...` 地址会迁移到新路径。
- 题目详情可以展示答案、运行上下文、发布复核和原文证据。
- HTTP 400 默认进入有限重试，不再一次失败后直接终止。
- 结构化输出请求遇到 400 时会从 `json_schema` 降级到 `json_object`，
  再次失败后移除 `response_format`；尝试次数仍受 Provider 重试上限约束。
- 主 Agent 的 Provider 摘要只保留一份材料预览、有限检索历史和截断后的检索理由，
  避免运行越久 payload 无限增长。
- Provider 明确指出上下文超长时，重试请求会自动压缩材料预览、检索历史和长字符串，
  而不是原样重放同一个超限请求。
- Provider 错误会保留脱敏响应和 request ID，并通过恢复事件进入运行诊断。
- `RECOVERY_REQUIRED` 会记录中断前状态、最后成功步骤和下一步。
- 新增 `POST /api/objective/{run_id}/resume`，使用原 `run_id` 从断点继续。
- 长时间无进展的 `stalled` 任务也允许恢复，并优先执行已经落盘但尚未完成的最后一个动作。
- 重复出现的短 claim ID 在内容冲突时自动改写为语义级稳定 ID，避免恢复时再次触发
  `artifact ... has different content`。

  Vite 生产构建通过。
