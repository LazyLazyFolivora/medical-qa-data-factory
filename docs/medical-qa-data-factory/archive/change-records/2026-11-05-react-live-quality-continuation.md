## 分开看评审与状态

两次评审均 REJECT，但不是“5 个候选都已被系统拒绝”。最终第一个候选经 close_candidate 进入 INDETERMINATE，其他四个仍为 PROPOSED，其中英文候选已有 REJECT 评审意见。质量意见和运行状态是分开的。

拒绝这些具体题目的方向基本合理，但评审把“给出选项/候选列表”一概视为泄露答案或无检索价值，理由过度泛化。有限候选集合也可能需要真正的外部检索和多条件整合，应按实际最短解题路径判断，不能按形式一刀切。

## 暴露的核心缺口

1. 新观察确实被用到了，但选题仍在围绕现有图谱边拼分类/枚举，没有建立自然、有意义的用户问题。
2. 用多个疾病名、列表长度、筛选条件数量冒充困难，未证明每个查询步骤都不可省略。
3. 将当前拿到的部分图谱记录写成“所有相关亚型”，没有证据证明范围完整。
4. 出题仍泄漏内部语境（“提供的证据”“明确列举的实体”）；主 Agent 的设计指令与真正返回的题目也不完全一致。
5. 工具引用依旧过长，模型抄错 ID、超出一次读取数量。候选引用应改善可用性，但这不能替代出题方法论。

下一步应优先用这些真实负例修订难题设计与候选评审 skill：先说明自然信息需求和必要查询依赖，再按证据决定能否成题；允许得出材料不够的结论，不强行拼题。引用方式可单独改善，不能再靠增加拒绝规则解决题目质量。
