# 探索规划的上下文压缩

## 遇到的问题
每次选择探索方向时，规划器都会重新读取已查过的方向、检索结果、事实和候选评审。随着轮数增加，旧材料反复占用窗口。此前一次请求在压缩后仍估算为 28,168 tokens，超过 27,648 的输入预算。这条日志说明只压一次不能保证请求能发出，单凭日志也无法判断空间都花在了历史还是当轮证据上。

## 讨论过的方案
程序可以精确记录查过哪些条目、题目状态和剩余轮数。把多轮结果归纳成“哪些方向有用、哪条线索仍缺什么”需要理解文字，交给 LLM。按需更新一张可恢复的便签，可以避免每轮重复总结。

## 实施计划和验收
1. 发出探索请求前，连同提示词、技能和输出格式一起估算大小。低于已有阈值时直接规划。
2. 接近窗口上限时，把部分历史和上一张便签发给摘要模型。保存新便签及其覆盖记录。重启后继续使用，尚未覆盖的材料仍以原文给规划器。
3. 目标、候选当前结果、计数和剩余轮数由程序直接传递。独立补证、答案验证和发布复核继续使用各自的输入。摘要不能充当发布证据。
4. 用本地测试覆盖触发、增量更新、断点恢复和预算边界。单批证据过大仍由证据侧处理。

## 实际改动
- Web 新任务、断点继续和 CLI 的外层探索共用同一套处理。沿用模型配置中的触发比例，默认是可用输入预算的 85%。输入预算已经扣除了输出预留和安全余量。
- 历史包括探索查询、检索结果概况、事实和候选评审。按首次看到记录的顺序优先压旧内容。专用摘要角色把上一张便签和这批记录合成一张最多 1,600 字符的新便签。摘要请求也检查预算，特别大的单条历史会分段读取。
- 每个任务分别在运行目录的 `objective_runtime/exploration_memory/` 下保存便签、首次观察顺序和覆盖记录的内容指纹。整批摘要成功后才原子替换文件。恢复旧断点时，如果其材料与已覆盖内容不一致，就从快照重建。完整证据仍在原任务快照中。
- 探索请求中的候选当前结果、目标和配额直接取自快照。盲搜与发布复核使用原有证据链。若仅当轮输入就超限，压缩历史无法保证解决。

## 验证结果
探索便签、调度、模型适配器、提示词和 Web 接口相关测试共 93 项通过。其中一项通过本地 HTTP 模拟服务发送实际格式的请求，覆盖两个各 50,000 字符的事实从触发摘要到继续规划、重新打开任务复用便签的过程。线上模型的摘要质量仍需用真实长任务观察。
