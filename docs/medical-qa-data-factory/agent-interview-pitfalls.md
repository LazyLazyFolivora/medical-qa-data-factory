## 3. Agent 架构与状态管理

### 题号 22 / 62 / 73：固定 Workflow 与自主 Agent 的区别

**实际踩坑**

项目早期虽然使用了 LangGraph，也有“Agent 决策”和“工具轨迹”页面，但内部主要是一条固定 DAG：

```text
验证实体
  -> 查询邻居
  -> 策展证据
  -> 生成 claim
  -> 生成问题
  -> 校验
  -> 持久化
```

各节点之间没有真正的“观察当前状态后选择下一个动作”。页面看起来像 Agent，核心仍然是 Workflow。

后来迁移到 Objective Agent 后，又出现另一个问题：它虽然有决策循环，但“候选动作是否合法”和“工具是否真的可执行”没有完全对齐。

**根因**

1. 把“存在多个节点”误认为“存在自主决策”。
2. 没有明确区分 Workflow 的控制流和 Agent 的决策权。
3. 工具列表是静态的，但工具可执行性依赖当前实体类型、证据来源和运行状态。

**解决方法**

- 主 Agent 只输出结构化决策：

```text
retrieve_materials
understand_facts
design_questions
verify_answer
realize_question
review_release
stop
```

- 运行时负责检查动作是否合法。
- 每个动作明确目标子 Agent、输入 artifact、预算和参数。
- 固定 Workflow 只保留真正确定性的阶段，不把模型决策塞进没有选择空间的节点。

**面试表达**

> 我们不是一开始就用了真 ReAct。第一版是把固定 DAG 包装成了看似 Agent 的界面，后来发现模型没有真正的动作选择权。重构时把“模型决策”和“确定性执行门禁”拆开，模型只提案，状态迁移和发布由程序控制。

### 题号 8 / 95：共享 State 的代价

**实际踩坑**

共享 state 让每个节点都能读取当前证据、候选、预算和已发布结果，调试方便，但带来了：

- 状态字段不断增长；
- 节点返回值覆盖还是合并容易出错；
- 并发提交时出现 stale revision；
- 新字段加入后旧 checkpoint 摘要不兼容；
- 一次失败后很难确认哪些子任务已经提交。

**根因**

共享状态只解决了“数据能读到”，没有解决“谁能写、何时写、写后如何验证”。

**解决方法**

- 使用不可变 runtime snapshot。
- 每次状态变更形成新 commit。
- 使用 `expected_state_revision` 做乐观并发控制。
- 子 Agent 通过 child slot 提交结果。
- artifact、decision、operation 分别使用稳定 ID。
- 读取时先校验原始 commit 的 digest，再应用当前模型默认值。

### 题号 14 / 27 / 82 / 1803：最大执行范围与终止条件

**实际踩坑**

- Web 默认最大动作数一度只有 12，形成多题候选前就耗尽。
- 连续空检索仍继续尝试相同方向。
- 模型重复返回相同或近似动作。
- 预算耗尽曾被当成普通循环退出，随后仍尝试继续生成。
- “证据已足”“预算耗尽”“没有合法动作”一度落到相近终态。

**根因**

预算是控制流条件，不是输出语义。系统知道循环停了，却不知道“为什么停”。

**解决方法**

- 明确记录 stop reason：

```text
target_reached
evidence_exhausted
budget_exhausted
no_new_evidence
max_agent_actions
provider_failure
recovery_required
```

- 对连续空检索设阈值。
- 对重复决策做 fingerprint。
- 动作数、模型调用数和金额分别设预算。
- 程序级终止条件不能被模型自行绕过。

## 4. 上下文与记忆

### 题号 15 / 65 / 71 / 114 / 118：上下文超限

**实际踩坑**

某次 PHYHIP run 在第 28 步发生 400：

```text
model maximum context length: 32768 tokens
prompt contains at least:    32769 tokens
```

只超出 1 token，但旧机制重试时原样发送同一请求。最终：

- 内部重试 4 次失败；
- 用户恢复 6 次仍然失败；
- 每次恢复都重复同一个超长 payload。

当时 119 个 artifact 对应的主 Agent payload 约 109,000 字符，其中主要来源是材料 preview、搜索理由和检索历史。

**根因**

1. Tool 和 artifact 输出没有上下文预算。
2. 所有历史 provider result 都保留完整 preview 和 rationale。
3. 重试只重复请求，没有根据 400 的具体原因改变输入。

**解决方法**

- 主 Agent 只保留每个 provider result 的一份短 preview。
- `search_rationale`、query 和 search trace 设置长度上限。
- 检索历史只保留最近 12 条。
- provider result、材料和其他上下文 artifact 设置数量上限。
- 检测到 context-length 400 后，下一次请求自动压缩：
  - 材料 preview 从最多 8 份降为 1 份；
  - rationale 和 query 长字符串截断；
  - search trace 只留最近几轮；
  - 仍是超限时进一步缩小。
- 原始材料仍保存在 blob/artifact 中，页面详情不受影响。

**效果**

同一个实际快照的 Agent payload 从约 109,000 字符降到约 52,000 字符。

### 题号 111 / 119 / 125：摘要压缩与关键细节丢失

**实际踩坑**

对长结果做摘要会带来风险：冷门但关键的限定条件可能在摘要中消失。

例如：

- 研究人群；
- 剂量和时间窗；
- 物种；
- 特定亚组；
- 负向或冲突结果。

**解决方法**

- 摘要只用于 Agent 规划，不作为最终证据。
- 原始材料、span、offset 和 hash 完整持久化。
- 最终答案验证重新读取原始证据锚点。
- 详情页区分“规划摘要”和“原文证据”。

**面试表达**

> 我们不允许摘要成为事实来源。摘要只帮助模型决定下一步，真正的 claim 和最终答案必须能回到原文 anchor。

## 5. 工具调用与 Skill

### 题号 16 / 133：工具存在不等于工具可用

**实际踩坑**

PubMed Skill 在动作上显示 available，但当前候选是一条来自非 CTD 的 PrimeKG 边。真正执行时返回：

```text
pubmed_evidence_insufficient
source_not_ctd
```

另一个例子是 Agent 从 gene/protein 实体出发查询 `anatomy_anatomy` 关系，持续得到空结果。

**根因**

工具注册表和执行前置条件分离。系统只检查“工具是否存在”，没有同时检查：

- Provider 是否支持当前来源；
- 实体类型是否符合关系语义；
- 必需输入 artifact 是否存在；
- 幂等状态是否允许再次执行。

**解决方法**

- 动作可用性不只看工具名，还检查能力声明和前置条件。
- 执行失败要记录稳定错误码。
- 对类型不匹配关系直接做策略拒绝。
- 连续空结果不能继续重复相同方向。
- UI 区分“策略接受”“执行成功”“执行失败”“结果为空”。

### 题号 216：JSON Schema 通过后为什么不能直接执行

**实际踩坑**

模型可能输出完全符合函数参数 schema 的 JSON，但工具仍不可执行，例如：

- 实体类型不匹配；
- Provider 不支持该来源；
- 缺少权限；
- 数据快照过期；
- 引用了不存在的 evidence anchor；
- 动作在当前 run state 下非法。

**解决方法**

执行前至少经过：

```text
JSON Schema
  -> 业务枚举
  -> 状态允许
  -> 实体/关系类型
  -> Provider 前置条件
  -> 权限与预算
  -> 幂等检查
```

### 题号 250 / 1792：重试与幂等

**实际踩坑**

重试模型或工具调用时，系统还出现过相同 artifact ID 对应不同内容的冲突：

```text
artifact claim_1 has different content
```

如果没有幂等键，恢复会重复写材料、重复生成 claim 或重复发布题目。

**解决方法**

- 网络、超时、429、5xx：有限指数退避。
- 400：读取 Provider 错误并分类，不能无条件原样重试。
- 操作使用稳定 `operation_key`。
- 每个 attempt 有独立 `attempt_id`。
- child slot 已提交时直接复用，不重新执行。
- artifact 内容必须不可变；相同 ID 不同内容直接冲突。

## 6. 失败定位与可恢复性

### 题号 4 / 36 / 75 / 99：崩溃、Checkpoint 和断点恢复

**实际踩坑**

早期只记录“任务失败”，但没有足够信息回答：

- 哪个子 Agent 失败？
- 失败发生在第几步？
- 上一次成功提交是什么？
- 下一步应该从哪里开始？
- 已经有哪些副作用？

**解决方法**

每个恢复状态记录：

```text
run_id
commit_sequence
run_state
last_successful_step
next_step
resume_count
recovery_state
last_error
provider_response
request_id
attempts
```

恢复流程：

```text
加载最后有效 commit
  -> 检查已提交 child slots
  -> 恢复中断前 run state
  -> 从 next_step 继续
  -> 使用原 run_id
```

**注意**

恢复不是“重跑整个任务”，而是从最后一个已验证检查点继续。

### 题号 67：模型、检索还是工具的问题

**实际错误现场**

一条 run 中：

```text
第 17 步：材料检索完成
第 18 步：主 Agent 决策模型返回 HTTP 400
```

仅看页面“生成失败”无法定位。记录完整上下文后才能判断：

```text
failure_step = 18
role = objective_main_agent
provider = main model
error_code = model_bad_request
attempts = 4
root_cause = context_length_exceeded
```

**解决方法**

每个步骤记录：

- action；
- target role；
- input artifact IDs；
- output artifact IDs；
- Provider；
- request ID；
- error category；
- retry count；
- elapsed time；
- stop reason。

## 7. Multi-Agent 状态与冲突

### 题号 44 / 45：事实冲突如何仲裁

**实际踩坑**

出现过：

- 多篇文献支持不同风险方向；
- 同一关系的 population、dose 或 study type 不同；
- 同一事实在不同证据包中被表述成 association 或 causality；
- claim 被模型判定为支持，但原始证据只提供背景。

**解决方法**

- 只有当上下文和限定条件一致时才比较方向。
- 不同研究上下文分别成组。
- 同一上下文内部冲突则拒绝发布。
- 关系强度不能由模型自行升级。
- 发布状态由确定性验证器控制。

### 题号 51 / 52 / 70 / 72 / 101：上下文污染与错误执行者

**实际踩坑**

- 主 Agent 和子 Agent 如果共享全部历史，容易读到不相关材料。
- 不同 run 的 UI 数据可能被拼在一起。
- 子 Agent 选错后会出现重复查询或来回踢皮球。

**解决方法**

- 每个子任务只接收任务目标和明确的 input artifact IDs。
- 子 Agent 不直接写全局 state，只提交 result 和 artifact。
- 主 Agent 决定下一步，但动作必须通过 validator。
- 每个 run 使用稳定 ID，前端查询不跨 run 混用。
- 重复决策使用 loop guard。

## 8. 结构化输出

### 题号 210–213：多余解释、JSON 错误、非法字段

**实际踩坑**

- 模型返回 JSON 前后附带自然语言；
- JSON 可解析但字段不符合契约；
- schema 不支持的 Provider 返回 400；
- 修复 Prompt 后仍然输出错误结构。

**解决方法**

- 使用 Pydantic 契约和严格 JSON Schema。
- 支持 Provider 能力降级：

```text
json_schema -> json_object -> prompt_only
```

- 不允许无限修复，最多进行有限次 schema repair。
- 错误分为：
  - parse error；
  - schema error；
  - bad request；
  - provider unavailable；
  - timeout。
- 最终无法满足契约时保留检查点，不输出半结构化成功结果。

### 题号 219：流程问题还是 Prompt 问题

**实际例子**

一次模型 400 看起来像“模型不支持 JSON”，实际 Provider 响应明确写着：

```text
context length exceeded
```

根因是 Agent payload 太长，不是 Prompt 约束写错。

**经验**

不要看到 400 就先改 Prompt。应先检查：

- 实际输入长度；
- Provider 支持的输出模式；
- 请求参数；
- 模型和 endpoint；
- 错误响应体；
- 是否是确定性可修复错误。

## 9. 质量与评估

### 题号 13 / 23 / 230 / 252：Agent 成功不能靠偶然

**实际做法**

- 候选事实必须有 evidence anchor。
- 答案必须有独立验证。
- 题面必须经过发布复核。
- 0 题是合法结果，不为达到目标放宽门禁。
- 每个失败状态都有稳定代码。
- 关键路径覆盖单元、集成和真实只读 Provider 测试。

**不足**

目前还没有完整的大样本人工抽样统计，也没有多模型、多 Prompt 的正式消融表。因此不能把单元测试通过说成“真实医学任务成功率达到某个百分比”。

### 题号 34 / 37 / 90 / 239

这些题需要谨慎回答。

我们已经具备：

- 模型 Provider 配置；
- 运行 trace；
- 确定性质量门禁；
- 单任务回归测试。

但还没有完成：

- 强模型与弱模型的受控 A/B；
- 单 Agent 与多 Agent 的完成率/成本对照；
- 运行时设计与模型升级的收益拆解；
- 完整 Recall、Precision、人工通过率和延迟报表。

面试时应该讲“我们有什么证据”，而不是把尚未完成的评测包装成已有结论。

## 10. 推荐面试表述

### 上下文超限

> 我们遇到过模型窗口只超 1 token 的 400。最初重试只是重复同一请求，连续失败多次。后来定位到 artifact summaries 和检索历史无限增长，改成原始证据完整持久化、模型只读取有界摘要，并在 context-length 400 后主动压缩下一次请求。实际快照从约 109k 字符降到 52k。

### 断点恢复

> 我们把每个决策、子 Agent 结果和 artifact 作为 runtime commit 保存。失败记录最后成功步骤、下一步和错误详情。恢复沿用原 run ID，从检查点继续，并通过 operation key 和 child slot 避免重复执行。

### 工具可执行性

> 我们踩过一个“Skill 可见但不可执行”的坑。PubMed Skill 本身可用，但候选证据边不是 CTD 来源，执行返回 `source_not_ctd`。后来明确把工具发现、策略接受和实际执行结果分成不同状态，并在动作规划阶段检查前置条件。

### 多 Agent 隔离

> 主 Agent 不把全部历史复制给每个子 Agent，而是传任务目标和明确的 artifact 引用。子 Agent 只能提交结构化结果，不能直接改全局发布状态。这样既减少上下文污染，也方便审计和恢复。
