# 生成任务增量存储方案

状态：设计草案；第一阶段已在重构分支实现，尚未部署。
日期：2026-11-19。

本文讨论生产任务如何在 PostgreSQL 和文件系统之间分配数据，替代当前逐次保存完整运行快照的方式。目标是保留数据集、Agent 执行记录、必要证据和断点恢复能力，同时消除重复存储。

## 1. 重构前的实现及问题

重构前，一次运行使用一个 `run_id`。自动生产流程中，一个 run 对应某个实体的一次生成尝试；同一实体可以有多次运行，一次运行可以生成多道题。

```text
data/runs/production/objective_runs/<run_id>/
├── objective_runtime/commits/
│   ├── 00000001.json
│   ├── 00000002.json
│   └── ...
└── debug_trace/
```

核心实现位于 `src/medical_qa_data_factory/generation/objective_question_runtime.py`：

- `ObjectiveRuntimeSnapshot` 同时包含当前状态、累积决策、子任务记录和完整 artifacts。
- `_commit_next()` 增加版本号，再调用 `_write_commit()` 写入整个新快照。
- `_merge_artifacts()` 将新产物加入累积集合；旧产物继续出现在之后的快照中。
- `record_decision()`、`register_child_slot()`、`commit_child_result()` 等分别产生提交，一次 Agent 动作可能产生多份完整快照。
- `ordered_decisions()` 和完整性校验依赖历史提交，不能直接删除旧 JSON 来完成改造。

此外，`llm/run_trace.py` 保存独立调试文件，部分工具日志包含完整 artifacts，模型请求日志包含请求正文，形成额外重复。

本地已有运行样本的统计如下。这里不是服务器 24G 数据的统计，也不代表改造后的空间承诺。

| 样本 | 提交数 | 提交文件累计大小 | 最新完整快照大小 |
|---|---:|---:|---:|
| A | 150 | 649.56 MiB | 5.98 MiB |
| B | 173 | 568.29 MiB | 5.97 MiB |
| C | 162 | 516.78 MiB | 5.25 MiB |

## 2. 保存哪些数据

| 类别 | 必须保存的内容 | 目的 |
|---|---|---|
| 最终数据集 | 题目、答案、解释、验证结论、来源引用、版本 | 发布、训练与评估 |
| Agent 记录 | 动作、参数、输入输出引用、执行结果、时间顺序 | 审计、分析、轨迹训练 |
| 材料与证据 | 材料内容、来源定位、获取时间、内容哈希 | 复核答案、支撑后续步骤 |
| 断点状态 | 当前阶段、候选题状态、待执行任务、预算、最后应用的事件序号 | 恢复运行 |
| 配置与版本 | 模型配置、提示词和 skill 版本、工具版本、生成参数 | 解释结果、重建运行条件 |
| 执行账本 | 操作标识、尝试次数、执行状态、结果引用、消耗 | 防止重复执行、重复发布和错误计费 |
| 关联信息 | 批次、实体、run、步骤、题目、材料之间的引用 | 查询、导出、判断能否清理 |

配置中不保存密钥。若要求重建历史模型输入，不能只记录可能失效的版本名称，应保存实际模板版本内容或可长期获取的内容引用。

## 3. PostgreSQL 与磁盘的分工

原则：数据库管理结构化记录、状态和关系；磁盘管理较大的不可变内容及导出文件。一个内容只存一份，其他位置通过 ID 引用。

| 数据 | 建议位置 | 写入方式 |
|---|---|---|
| 批次、实体、运行 | PostgreSQL | 创建记录，更新当前状态 |
| 最终题目及验证结论 | PostgreSQL | 结构化保存，发布版本不可变 |
| Agent 事件 | PostgreSQL | 每个事件追加一次 |
| 操作及执行尝试 | PostgreSQL | 每次尝试独立记录，更新执行状态 |
| 最新断点 | PostgreSQL | 保存精简状态，不内嵌历史与材料正文 |
| 配置版本 | PostgreSQL，较大模板可引用文件 | 每个版本保存一次 |
| 材料元信息和引用 | PostgreSQL | 保存类型、来源、位置、哈希和关联 |
| 小型结构化产物 | PostgreSQL JSONB | 作为独立产物保存，不塞进运行快照 |
| 材料正文、PDF、全文、大型工具返回 | `/data2` | 不可变文件，按内容哈希去重 |
| 完整模型输入输出、详细调试日志 | `/data2` | 独立记录，可压缩，设置保留策略 |
| 发布 JSONL、发布清单 | `/data2` | 按发布版本导出，不覆盖历史版本 |

大内容进入文件存储的阈值待确定。选择阈值时应考虑查询需求，不能仅依据字节大小拆分任意字段。

注意：将业务文件放在 `/data2` 不会迁移 PostgreSQL 自身的数据目录。数据库磁盘需要单独规划、迁移和备份。

## 4. 数据表草案

以下是逻辑职责，不是最终 SQL。实施时优先扩展现有生产表，避免另建一套重复的批次、实体和题目表。

| 表／记录组 | 主要字段或职责 |
|---|---|
| `runs` | run_id、实体关联、批次关联、配置版本、运行状态、状态版本 |
| `agent_events` | run_id、单调递增序号、事件类型、步骤 ID、操作 ID、时间、小型事件载荷 |
| `operations` | 操作幂等键、输入摘要、所属 run、当前操作状态 |
| `operation_attempts` | 尝试 ID、重试序号、开始结束时间、结果引用、错误、用量 |
| `run_checkpoints` | run_id、状态版本、最后应用事件序号、精简状态、状态格式版本 |
| `artifacts` | 产物 ID、类型、内容哈希、存储方式、文件位置或小型 JSONB、大小、创建时间 |
| `artifact_sources` | 产物的来源、来源标识、定位信息、获取时间 |
| `artifact_refs` | 哪个 run、事件、题目、发布版本或断点引用哪个产物 |
| `questions`、`releases` | 题目内容、验证结论、版本及发布成员关系 |
| `run_configs` | 模型与工具配置、模板版本、生成参数 |

事件序号在同一个 run 内唯一；操作幂等键和尝试 ID 需要唯一约束。更新断点时校验预期状态版本，防止并发覆盖。

内容哈希用于去重文件内容，不替代业务产物 ID。同一正文可能有多个来源和不同的获取时间，不能去重掉这些来源记录。

## 5. 文件目录草案

```text
/data2/medical-qa/
├── artifacts/
│   └── ab/cd/<content_hash>      # 独立、不可变的大内容
├── traces/
│   └── <run_id>/                # 模型输入输出、调试记录
├── releases/
│   └── <release_id>/            # 数据集 JSONL、清单、校验信息
└── staging/                     # 尚未完成提交的临时文件
```

材料不按实体重复保存。不同实体和运行可以引用同一内容文件。

数据库建议记录相对于存储根目录的文件键，由配置指定存储根目录，避免把 `/data2` 的具体绝对路径写死在每条记录中。

工作区应有稳定的 workspace_id，数据库身份不再由目录绝对路径计算。现有路径哈希 schema 的迁移需要显式建立旧工作区与新标识的映射，不能在迁移时自动切换到空 schema。

## 6. 一次步骤如何落盘

外部调用之前，先登记操作及其执行尝试，再发起调用；不在漫长的模型或检索请求期间持有数据库事务。

取得结果后：

1. 将新增大内容写入临时文件，计算并校验哈希。
2. 将内容可靠落盘并发布到不可变文件位置；已存在相同内容时复用。临时文件和最终文件应位于同一文件系统，以支持原子重命名。需要考虑文件和目录同步，而不仅是重命名成功。
3. 开启一个短 PostgreSQL 事务。
4. 登记产物元信息、来源和引用。
5. 追加 Agent 事件，记录此次结果。
6. 更新操作尝试状态、预算及最新断点。
7. 提交事务，才将该步骤视为已确认完成。

文件系统和 PostgreSQL 不是一个原子事务，因此采用“文件先就绪、数据库后引用”的顺序。

- 文件已写入、数据库未提交：产生孤立文件，留出安全缓冲期后回收。
- 数据库已提交：引用的文件必须已经可读；后续发现缺失时报告存储完整性错误，不能默默跳过。
- 清理任务必须避开仍在写入或等待提交的内容，不能看到暂时没有引用就立即删除。

## 7. 断点恢复与执行语义

恢复时读取最新断点、未结束操作和它们依赖的产物。若允许检查点落后于事件，重放其后的已提交事件；事件载荷必须足以恢复相应状态变化。

断点中只保存当前必要状态及引用，不保存全部历史决策和全部材料正文。旧检查点可以少量保留，但其引用的材料也必须被保护。

| 崩溃位置 | 恢复方式 |
|---|---|
| 外部调用尚未开始 | 继续执行待处理操作 |
| 结果和完成状态已提交 | 复用结果，不再次调用 |
| 请求已发出，但没有可靠保存结果 | 标记为结果未知，按供应商查询或幂等能力处理；否则显式重试并记录可能重复消耗 |
| 数据集发布已提交 | 用唯一约束和发布记录避免重复发布 |

不能承诺所有外部 API 都严格只执行一次。系统应保证本地结果提交和发布幂等，并显式记录外部调用的不确定状态。

## 8. Agent 记录与调试日志

Agent 事件是正式记录，保留动作、参数、输入输出引用、结果和用量。

调试日志包含完整请求体、原始响应和异常堆栈，单独设置保留期，不在事件中重复内嵌这些内容。

如果某条轨迹用于训练或需要准确重现模型当时看到的上下文，应保存实际输入，或保存能够准确重建输入的模板、材料、顺序、截断规则和参数。此类内容不能按普通短期调试日志自动清理。

## 9. 保留与清理策略

按时间清理的前提是检查引用关系和保留标记，而不是直接按文件修改时间删除。

| 内容 | 建议规则 |
|---|---|
| 已发布题目和关键支撑证据 | 长期保留 |
| 活跃任务、最新及保留检查点依赖的材料 | 不清理 |
| 被选为训练或评估数据的轨迹及依赖 | 随对应数据版本保留 |
| 已结束任务的临时材料 | 在不再承担恢复、复核、训练用途后按期限清理 |
| 完整调试日志 | 短期保留，错误任务可延长 |
| staging 与孤立文件 | 超过安全缓冲期、确认无活跃写入后回收 |

需要区分“历史记录提到某个材料”和“必须保留该材料正文”的引用。否则保留全部 Agent 历史会使任何材料都无法过期。

正文允许删除时，保留产物 ID、哈希、来源、删除时间和原因，并明确标记内容已清理。仍要求可复现的轨迹不得进入这一流程。

清理采用候选标记、再次检查引用、执行删除、记录结果的流程，并处理与新引用建立之间的并发竞争。

具体保留天数暂不写死，待确认生产量、审计需求和训练用途后配置。

## 10. 历史数据边界

按本次确认的要求，不适配历史存储。不提供旧 commits 导入、双格式读取或自动回退。新任务统一使用 PostgreSQL 增量存储，旧 run 不支持恢复。

旧文件由使用者决定如何归档或删除；代码不会自动删除。已有生产批次也不会因此被转换，切换版本时应停止旧任务，使用新的生产工作区建立新批次。

## 11. 备份与验收

数据库和内容文件共同构成完整系统，不能只备份其中之一。备份期间应保护其引用的内容不被清理；发布备份需要带清单和哈希，并实际进行恢复检查。

验收至少覆盖：

- 新增一个步骤不会再次写入所有旧材料正文。
- 相同内容跨 run 复用文件，同时保留各自来源信息。
- 事件顺序、最终题目、必要证据及预算记录在重新加载后保持一致。
- 在文件写入、数据库事务提交前后中断，均能恢复或明确报告未知状态。
- 重试不会造成重复发布；未知外部调用消耗不会被假定为零。
- 清理不会删除活跃任务、已发布题目或保留轨迹必需的内容。
- 改变磁盘根目录不会改变工作区数据库身份。
- 对实际样本比较总空间、每步写入量和恢复耗时，不预设压缩比例。

## 12. 待确认的取舍

1. Agent 记录是否全部长期保留，还是只长期保留进入训练集的轨迹？
2. 已发布题目需要保留完整原始材料，还是关键证据片段加可靠来源即可？不同材料类型可以采用不同规则。
3. 完整模型输入输出是否属于长期训练数据，还是默认仅作为短期调试记录？
4. 未发布、失败和零产出任务的材料保留多久？
5. 第一阶段是否仅实现去重材料、追加事件和最新断点，后续再增加自动清理？建议先保证写入与恢复可靠，再启用自动删除。

## 13. 第一阶段实现范围

实现位于 `generation/runtime_storage.py`，由 `ObjectiveRuntimeRepository` 调用。Web、持续生产与 CLI 统一使用 PostgreSQL 增量存储。

- `runtime_heads`：最新精简状态和完整性摘要。
- `runtime_items`：按集合、业务 ID 拆开的当前记录，仅更新发生变化的记录。
- `runtime_events`：每次提交的变更，记录增加、替换和删除，不保存完整历史快照。
- 大于 16 KiB 的单个内容对象进入哈希文件存储。artifact 的 payload 单独去重，来源等信封信息保留在数据库中。
- 一个 PostgreSQL 事务更新集合记录、事件和断点；并发提交校验序号。
- Web 进度时间和决策顺序直接读取数据库记录。

运行内存接口仍返回完整领域快照，降低的是重复持久化量，不承诺降低内存占用。单个集合条目的更新保存该条目的新版本，未将每个嵌套字段拆成独立数据库记录。

尚未实施：自动垃圾回收、引用保留策略、调试日志压缩与去重、原始材料缓存和全文文件的统一归档、工作区身份从路径哈希迁移到稳定 ID。

部署及配置见 [增量存储使用说明](incremental-storage-operations.md)。
